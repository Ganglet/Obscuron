## Pre-Development Decisions (Blueprint, July 2026)

### D1 — Layer 1 (calibrated novelty scoring) as the methodological core [Blueprint §7]
Five candidate architectures were scoped (§6). Layer 1 — calibrated novelty scoring over genomic embeddings — is the core, with Layer 3 (immune-inspired self/non-self) as a supporting theoretical narrative that reuses the Layer 1 embeddings at minimal extra cost. A scoped extension from Layer 2 (sequence–structure fusion) or Layer 4 (multi-signal convergence) is incorporated in the final phase only if time permits. Reason: Layer 1 has the strongest ratio of methodological novelty to what is implementable in one term on the available hardware. Alternative rejected as *primary*: Layer 2 (full structure prediction) — ESMFold is memory-constrained on 8GB VRAM (see D9).

### D2 — Retrospective (temporal) validation as the core evaluation strategy [Blueprint §2.5]
Dark matter has no contemporaneous ground truth, which blocks not just prediction but *evaluation*. Decision: freeze a reference-database snapshot at an earlier time T₀, score what was dark matter at T₀ using only information available then, and grade those scores against the current, more complete database — where some T₀-dark sequences have since been characterised. This manufactures a genuine, falsifiable test set. Known limitation carried forward (see D-risk in §10): the characterised-since set is *not* a random sample of dark matter — it is enriched for sequences that were already close enough to something known to become tractable, so the most genuinely novel cases may never enter the positive set. Stated explicitly, not treated as resolved.

### D3 — Genos-m primary, ESM-2 as formal fallback *and* comparison [Blueprint §7]
Genos-m (genomic foundation model) is the primary embedding source, but it is an unpublished May-2026 preprint — availability, stability, and reported performance cannot be assumed. Decision: adopt ESM-2 (protein language model) as a formal fallback *and* comparison pipeline, not an optional afterthought. Both embeddings are extracted in Phase 1 on a small labelled subset and their separation of known functional categories compared directly. This de-risks the Genos-m dependency and turns it into a research question — does genome-level context add value over an established protein-level model. If Genos-m underperforms or becomes unavailable at any phase boundary, ESM-2 becomes primary with no change to the surrounding methodology. Alternative rejected: Genos-m only — single point of failure on an unreviewed model.

### D4 — Open-set recognition framing; novelty as a calibrated score, not a class [Blueprint §6, Layer 1]
Dark-matter detection is formulated as open-set recognition: rather than forcing each sequence into a known category, model the boundary of characterised sequence space and assign a calibrated novelty score reflecting distance from it. The concrete scorer — extreme-value-theory (EVT) tail calibration vs density-based scoring (kNN / one-class / isolation forest) — is deferred to a Phase 2 decision, but the *framing* (open-set, ranked score, "none of the above" allowed) is fixed here. The project title commits to *calibrated* novelty, which biases the Phase 2 choice toward EVT as the headline with a density-based baseline.

### D5 — Evaluation metrics fixed before implementation [Blueprint §7]
To prevent post-hoc metric fishing, the evaluation metrics and the value(s) of K are fixed prior to Phase 2 and not adjusted based on results: (1) **Precision@K** — fraction of the top-K novelty-ranked candidates that were characterised between the historical and current snapshots; (2) **AUROC on a held-out-family sanity test** — a known family is temporarily withheld and the method's ability to flag it as anomalous is verified; (3) a **calibration check** comparing predicted novelty scores against observed characterisation outcomes. Complementarity: (2) tests sensitivity to novelty, (1) tests that the surfaced novelty is real, (3) tests that the score is honest.

### D6 — Go/no-go dataset gate [Blueprint §7]
The retrospective positive-label set size is estimated in Phase 1, before any modelling. Floor: a positive set of at least **50–100** characterised sequences is treated as the minimum for a stable AUROC estimate. If the projected count falls below this on the initially selected snapshot pair → widen the interval between snapshots, or broaden references (GTDB together with Pfam/UniProt updates), before Phase 2. If neither yields a viable sample → **Layer 5** (statistical discrimination of coding structure from noise, which requires no positive-label set) is promoted to the primary contribution.

### D7 — GTDB as the primary snapshot pair [Blueprint §2.5, §11]
The Genome Taxonomy Database (GTDB), being regularly versioned, supplies the historical/current snapshot pair for retrospective validation. Its release history gives well-defined temporal boundaries and provenance. Pfam / UniProt updates are held in reserve to broaden the characterised set at the go/no-go gate (D6).

### D8 — Target venues fixed in advance [Blueprint §7]
Primary: **ACM-BCB** (ACM SIGBio flagship; Scopus + Web of Science; equivalent 2027 deadline projected ~Feb–Mar 2027, giving ~3–4 months of manuscript runway after Phase 4). Fallback: **IEEE BIBM** (CCF-B; Scopus; 2027 cycle projected ~July 2027). Dates are projected from prior-year cycles and must be confirmed against the official calls for papers.

### D9 — Compute scope: audit-only on M1 Pro + RTX 4060 (8GB) [Blueprint §9]
No model training; forward inference on pretrained models plus lightweight statistical modelling (kNN, EVT, isolation forest) fits both configurations. The one constraint is full 3-D structure prediction (ESMFold) on 8GB VRAM → restrict to a small high-priority subset with sequence chunking, and prefer the ProstT5 approximation. If full-scale structure prediction is required, rent bounded cloud GPU capacity or request university-cluster allocation — raised early in Phase 1, not after the dataset is scoped.

### D10 — Phase 1 time-boxed at three weeks [Blueprint §7]
Phase 1 (reference-snapshot construction + embedding pipeline + go/no-go gate) is fixed at weeks 1–3. If GTDB snapshot-differencing is not complete by the end of week 3, the contingency is to *narrow scope* to a smaller set of taxa or gene families — the remaining schedule is not renegotiated. A partial, narrower benchmark that keeps Phase 2 on schedule is preferred over a complete benchmark that delays it.

### P1-D2 — Snapshot boundary: R207/Pfam-35 (T₀) → R232/InterPro-latest (T₁), justified by embedding-leakage alignment [Phase 1]
Confirms `config/snapshots.yaml` (was Track-1-pending). T₀ = GTDB R207 (Apr 2022) + Pfam 35.0 (Nov 2021); T₁ = GTDB R232 (Apr 2026) + InterPro-latest. The boundary is chosen for more than gap length. **The threat it addresses: temporal leakage through the pretrained embedding model.** Retrospective validity assumes the score reflects only T₀-era knowledge, but the embedding models postdate T₀ — a sequence dark at T₀ but characterised later can sit in the model's training data and be embedded near the family it was *later* assigned, contaminating the "novelty = distance" signal. Mitigation baked into the boundary: **ESM-2's UniRef50 training (~2021) is essentially aligned with T₀ (late 2021)** → the ESM-2 (protein) arm is near leakage-free; Genos-m (2026 preprint) sees the whole post-T₀ window → high leakage. So the planned ESM-2-vs-Genos-m comparison (D3) **doubles as a leakage-sensitivity probe**: a result stable across a low-leakage and a high-leakage model is not leakage-driven. This converts two standing risks (leakage; unpublished-Genos-m dependency) into one designed experiment. **Cutoffs now verified — see P1-D7:** ESM-2 = UniRef50 2021_04 (clean, ≈T₀); Genos-m = GTDB R220 / Apr 2024 (in-window → leakage-controlled, ESM-2 becomes the clean headline). Also planned: one shorter, more recent gap as a robustness point so the headline is not hostage to a single boundary. Alternative rejected: a more recent T₀ — would misalign with ESM-2's cutoff and *increase* protein-arm leakage.

### P1-D3 — Operational definition of "dark at T₀" and "characterised by T₁" [Phase 1]
Answers the two open questions in `docs/reproducibility.md`. **Sequences** = GTDB representative-genome proteins (`gtdb_proteins_aa_reps`) — the material that gets scored. **Dark at T₀** = a GTDB protein with *no* Pfam-35.0 domain hit at the family gathering (GA) threshold (standard `hmmscan` with GA cutoffs). **Characterised by T₁** = that protein now matches a family that is *new since T₀* — Pfam-37/InterPro-latest; since Pfam froze at 37.0 (Jun 2024) the **current signal is InterPro-latest**, not Pfam. **Positive label** = dark-at-T₀ ∧ characterised-by-T₁. The still-dark remainder is **unlabelled, not a true negative** (could be genuinely non-functional or merely not-yet-characterised) — the fundamental limit of the design, stated not buried. **GTDB taxonomy is not the function signal**: it supplies the sequences and a universe-growth number, nothing about a gene gaining function. Selection-bias caveat (D2/blueprint §10) still holds: characterised-since sequences skew to the *near-known*, so the positive set is moderate-novelty, not maximal — governs what Precision@K actually rewards.

### P1-D4 — Data provenance & subsetting standard: stream public data, persist only derived artifacts, subset the benchmark [Phase 1]
Prompted by the S3 bill (~$12/3mo for ~166GB of protein FASTAs) and Track 2's R207 re-upload. Two facts: (a) GTDB FASTAs are permanently, freely hosted (ace.uq.edu.au / data.gtdb.ecogenomic.org) — warehousing them in S3 pays to duplicate free, re-downloadable data; (b) the full rep-protein set (~10⁸ proteins for R207) cannot be embedded on local hardware anyway. **Standard set (Track 1 owns provenance):** raw reproducible public data is *never* warehoused; the pipeline streams the needed sequences from the public mirror (range-request capable) through hmmscan/embedding and **persists only derived artifacts** — embeddings, dark/characterised labels, and a manifest recording source URLs + checksums. **Subset the benchmark** to a principled *stratified* taxonomic sample (needed for local compute regardless of cost; sampling design is a documented methodological choice to avoid taxonomic bias). **Defer** R232 proteins (application-time, not the validation gate) and `nt_reps`/`genomes` (174/179GB — roughly triples the bill). If any S3 staging is kept, apply a 30–60 day lifecycle-expiry. Net persistent footprint: GB-scale derived data → cents. Cross-track: relay to Track 2 before the R207 re-upload finishes — it may be unnecessary. The finalize-time "checksum bug" is almost certainly the S3 multipart-ETag gotcha (ETag = MD5-of-part-MD5s + `-N`, not the file MD5); robust fix is `ChecksumAlgorithm=SHA256`.

### P1-D5 — Go/no-go PROXY result: gate passes by 2–3 orders of magnitude [Phase 1]
Proxy pulled from Pfam release notes before building the full differencing pipeline. Pfam **35.0** (Nov 2021, ≈T₀) = **19,632** families (76.90% UniProtKB coverage); Pfam **37.0** (May 2024, ≈T₁) = **21,979** families (77.08%) → **+2,347 net new families** across the interval (37.0 relnotes alone: 1,196 new, 12 killed, in 36→37). Each new family is by construction a cluster that went dark→characterised. Floor is 50–100 positive-label sequences (D6). Even one GTDB member per new family clears it; realistically dozens of members each, microbe-dominated → positive-label population **~10⁴–10⁵**. **Availability is not the binding constraint; local embedding compute is (→ subset, P1-D4).** Caveat: this is the Pfam/UniProt-wide proxy (slightly optimistic — some new-family members were not dark in the GTDB rep set); InterPro-latest as the current signal (P1-D3) would only raise it. **Definitive count deferred to the Week-2 hmmscan** (`hmmscan(R207-reps, Pfam-35)` → dark; `hmmscan(dark, InterPro-latest)` → characterised). Gate: **GO.**

### P1-D6 — Benchmark subset spec: stratified genome panel + budgeted embedding [Phase 1]
The full R207 rep set (~10⁸ proteins) cannot be embedded locally and warehousing is out (P1-D4), so the benchmark is a principled subset. Two-stage design (all three open choices confirmed with Track 1):
- **Stage 1 — genome panel.** GTDB R207 species-reps stratified by GTDB phylum. Per phylum: `n = clip(round(f·N_phylum), floor=2, cap=30)`, with `f≈2%` tuned so the panel totals **G ≈ 500** genomes. Scheme = **proportional-with-floor-cap** (chosen over equal-per-phylum and pure-proportional): the floor guarantees the rare candidate phyla — CPR/DPANN, where dark matter concentrates — appear; the cap stops Proteobacteria/Firmicutes dominating. Sampling seed fixed and recorded.
- **Stage 2 — label (CPU, Track 2).** `hmmsearch` panel proteins vs **Pfam-35 profiles** (fast direction) → dark = no GA-threshold hit; vs **InterPro-latest** → **positive = dark-at-T₀ ∧ hits an InterPro entry that postdates T₀** (new-family condition; excludes threshold-artifact false positives). Characterised-at-T₀ (has a Pfam-35 hit) = the known-boundary reference.
- **Stage 3 — embed (GPU / M1 Pro).** Target **~50–80k** embeddings: **all positives** (never subsampled), a capped dark-negative query universe (~20–40k), and a stratified characterised reference (~20–40k, per-phylum cap).
- **Pilot first.** Label a **50-genome pilot** to *measure* the real dark-fraction and positive-rate on GTDB microbial data (the ~20–40% dark / ~0.5–1% positive-rate figures are UniProt-wide extrapolations), then set G from the measured rate. Expected positives at G=500: ~1,000 (pessimistic 0.3%) to ~2,800 (~0.8%) ≫ the 100 floor — robust to a 3× rate error.
- **Held-out-family AUROC (blueprint metric 2) reuses this panel** — hundreds of genomes give thousands of families to hold out.
- **Cross-track:** Track 2 implements the sampler against `taxonomy.csv`, runs the pilot, then Stage 2/3. Track 1 owns the parameters (f, floor, cap, G, budget, seed) and the allocation scheme.

### P1-D7 — Model training cutoffs verified; per-arm leakage handling (ESM-2 = leakage-clean retrospective headline) [Phase 1]
Verified the cutoffs behind the P1-D2 leakage argument. **ESM-2** = UniRef50 **2021_04** (~late 2021); Pfam-35 was built on UniProt 2021_03 and T₀ = R207 (Apr 2022), so ESM-2 predates every T₀→T₁ characterisation event → **leakage-clean**, and the R207/Pfam-35 boundary is empirically validated. **Genos-m** (model card) = pretrained on **GTDB R220** (released **24 Apr 2024**) + human-microbiome MAGs/UHGV phages — R220 is *inside* the T₀(2022)→T₁(2026) window and is the *same database* the benchmark draws from, so Genos-m has already seen the benchmark sequences and any 2022→Apr-2024 characterisation events leaked. Nuances: Genos-m is **self-supervised** (raw DNA, no family labels) → a weaker leak than a supervised model; and the likely direction is **conservative** (seen sequences cluster near homologs → *lower* novelty → *harder* to flag), so a positive Genos-m result would be despite the leak, not because of it.
**Decision:** (1) **ESM-2 is the leakage-clean retrospective headline** — the trustworthy validation of the method. (2) **Genos-m positives restricted to post-R220 (Apr 2024→T₁)** for a clean number, *and* reported over the full 2022→T₁ window so the gap **quantifies the contamination** (a result in itself; margin from P1-D5 affords the shorter window). (3) Genos-m stays the **novel genome-FM substrate** and the genome-vs-protein comparison, reported leakage-controlled. This reframes the blueprint's "Genos-m primary": ESM-2 carries the clean retrospective validation, Genos-m the caveated genome-context angle — net design is *stronger* (two models, explicit leakage control), not weaker. Supersedes P1-D2's "verify cutoffs" TODO. Sources: facebookresearch/esm (UniRef50 2021_04); Genos-m model card + GTDB R220 release date (24 Apr 2024).

### P1-D8 — Pfam-37 net-new-family proxy stands in for InterPro-latest [Phase 1, Track 2]
Track 1's operational definition (P1-D3) specifies InterPro-latest as the "characterised by T1" signal. Full InterProScan is a much heavier lift than anything else in the pipeline — ~6.6GB of data across roughly ten bundled member-database search tools (not just HMMER), realistically needing Docker on this Windows machine. Decision: use a Pfam-37 net-new-family proxy instead — a protein counts as characterised-T1-proxy if it hits a Pfam-37 family that's new since Pfam-35, reusing the same mechanism behind Track 1's own go/no-go proxy estimate (P1-D5). Verified Pfam family counts exactly match Track 1's cited numbers (35.0: 19,632 families; 37.0: 21,979). Limitation stated, not buried: this proxy is narrower than true InterPro-latest — it misses cases where a sequence is newly characterised only via a non-Pfam member database, so the real positive count should only be larger. Alternative rejected for now: full InterProScan via Docker — left as a follow-up if the proxy's fidelity becomes a real concern, not attempted first given the setup cost relative to the time available. Ran across the full 502-genome panel: 4,138 positive-proxy sequences — 41-83x the 50-100 floor (D6).

### P1-D9 — Genos-m needs nucleotide sequences, not the protein reps already fetched [Phase 1, Track 2]
Problem, not a decision: every sequence fetched and extracted through Week 2 (`gtdb_proteins_aa_reps`) is amino-acid protein — correct for ESM-2 and the Pfam differencing pipeline, but Genos-m does single-nucleotide tokenization and cannot take protein as input. Protein can't be reverse-derived into its source DNA either (the genetic code is degenerate — multiple codons map to the same amino acid), so this needed a fresh fetch, not a transform of what already existed. Flagged externally by Track 1 before it was caught internally. Fix: built a separate extractor (`src/darkmatter/data/panel_nucleotides.py`) pulling `gtdb_proteins_nt_reps` directly from GTDB's public mirror (not through S3 — no AWS credentials needed, consistent with the provenance standard of streaming what's needed rather than warehousing, P1-D4). Confirmed the archive's gene calls match the protein version exactly per genome (e.g. 219/219), so the existing panel's accession list applies unchanged. Ran to completion: 502/502 genomes, 1.4GB.

### P1-D10 — Full-panel runs need fine-grained checkpointing, not just per-file idempotency [Phase 1, Track 2]
Problem: multi-hour full-panel operations (protein extraction, Pfam labeling, nucleotide extraction) were repeatedly killed mid-run by environment/session restarts outside the pipeline's control — three separate times for the labeling step alone, twice more for the nucleotide extraction (once from a confirmed genuine network/DNS outage, not a code bug). Being resumable only at the level of "skip files already fully written" isn't enough when a single run item (one Pfam scan pass, one archive scan) itself takes tens of minutes to hours. Decision: (1) batch multi-hour operations into small chunks (25 genomes) that checkpoint to disk after every chunk, not just at the end of the whole run; (2) for pure network operations, add OS-level crash resilience — a bash retry-loop wrapper, a logon-triggered resume task, and a periodic watchdog that kills and restarts a hung-but-not-crashed process — mirroring the pattern already built in Week 1 for the S3 transfer. Without this, both the full-panel labeling run and the nucleotide extraction would have had to restart from zero after every interruption instead of losing only the in-flight chunk.
### P1-D11 — Novelty claim narrowed; closest prior art + differentiators (Phase-1 literature search) [Phase 1]
Systematic search run for the §4 deliverable (web + arXiv + PubMed + bioRxiv). The blueprint's broad claim ("no work applies a calibrated novelty score to a microbial genomic FM") is **not defensible as written** — narrowed. Closest prior art:
- **HiFi-NN** (iScience 2025, PMC12148589) — nearest by target ("annotating the microbial dark matter," ESM-2 650M embeddings). But: (a) it **annotates** (assigns EC numbers = closed-set label transfer), not novelty detection; (b) calibration = heuristic softmax-kNN confidence + hard distance cutoff (0.38), **not** conformal/EVT; (c) **no** open-set "none-of-the-above" (can't separate low-confidence-known from novel); (d) its temporal split (244 post-Jul-2023 Swiss-Prot seqs) is a minor benchmark, not leakage-controlled. Uses ESM-2 650M → independently validates our protein-arm choice.
- **DeepVirus / viral-dark-matter hierarchical DL** (bioRxiv 2025) — open-set recognition + protein FM + genome context + novel-group detection, but **viral lineage taxonomy** (not bacterial/archaeal function) and hypothesis-testing open-set (not EVT).
- Neighbourhood: anomaly detection on protein embeddings (NAR GB 2024); EVT open-set in general ML (EVM/OpenMax); temporal-holdout function prediction (FUGAsseM, Nat Biotech 2025; CAFA); protein-embedding uncertainty (Nat Methods 2026).

**Refined novelty claim (defensible):** first to cast microbial **functional** dark-matter prioritisation as **formally-calibrated open-set novelty detection** — an EVT novelty score with a *checked* error rate, not annotation — validated by a **leakage-controlled** retrospective benchmark contrasting a leakage-clean protein FM (ESM-2) vs a genomic FM (Genos-m). Differentiators: novelty-not-annotation (vs HiFi-NN); formal EVT calibration (vs HiFi-NN's heuristic cutoff / DeepVirus's hypothesis test); microbial functional (vs DeepVirus's viral lineage); leakage-controlled retrospective (vs everyone's plain temporal holdout). **Honest caveat: retrospective validation itself is NOT novel (CAFA/FUGAsseM/HiFi-NN all use temporal holdout) — frame the retrospective contribution as the LEAKAGE CONTROL (P1-D7), not the holdout.** Related Work must foreground HiFi-NN + DeepVirus. Re-run the search immediately before submission (blueprint §7).

### P1-D12 — Genos-m arm needs NUCLEOTIDE input; small matched separation set first, full-64k deferred [Phase 1]
Reviewing the full-panel Genos-m run Rayyan requested on the M1 Pro. The blocker is **not memory** (M1 Pro loads Genos-m fine, P1-D1). `scripts/embed_panel_sample.py` loads amino-acid `*_protein.faa` and feeds the *same strings* to whichever `--model` is passed — but **Genos-m is a nucleotide/DNA model** (single-nt tokenisation, N-run preprocessing, trained on GTDB genomes). Feeding it amino acids produces meaningless embeddings **and** defeats the genome-vs-protein comparison. The Genos-m arm requires the **nucleotide gene sequences** (`gtdb_proteins_nt_reps`) — deferred in P1-D4, not fetched; and `panel_proteins/` is not even present locally on the M1 Pro. Not a Rayyan error — the ESM-2 (protein) arm was built/validated; the Genos-m (DNA) arm's nt path was never wired since his 4060 couldn't load the model anyway.
**Decisions:** (1) Track 2 fetches the panel's **nt gene sequences** (R207 `nt_reps` subset — only the ~500 panel genomes, streamed per P1-D4, not the full ~174GB) and adds a nucleotide-loading path to the embed pipeline for `--model genos-m`. (2) **Do NOT run full-64k Genos-m on the M1 Pro** — 4.7B MoE on MPS over DNA genes up to 8 kb ≈ many hours–days, and Genos-m is only the leakage-contaminated *comparison* arm (P1-D7), not the headline. (3) **Run Genos-m first on the small matched separation set** — the same ~100 seqs / 30 genomes / 20 Pfam-35 families Rayyan used for the ESM-2 separation check, as nucleotides → fast on the M1 Pro, directly answers "is Genos-m's genome-context separation comparable to ESM-2's gap of 0.036?". (4) Full-64k Genos-m embedding (for the Phase-2 novelty scorer) deferred to cloud/cluster (D9) if needed.
**Phase-1 numbers validated** (experiment_log 2026-08-13): 1,341,100 proteins → 22.21% dark-at-T₀ (P1-D3 estimate ✓), 4,138 positives = 0.309% (41–83× the floor; matches P1-D5's pessimistic 0.3%). ESM-2 t33_650M separation gap = 0.036 (within-family 0.963 vs across 0.928).

### P1-D13 — Embedding-extraction protocol fixed (identical-except-modality) [Phase 1, Track 1]
Closes the last Phase-1 Track-1 deliverable (§2). A sequence → a vector *identically across both arms except the one necessary difference — protein vs nucleotide input* — so any genome-vs-protein result is attributable to the model, not preprocessing.
- **Modality:** one gene set, two representations. ESM-2 ← aa CDS (`gtdb_proteins_aa_reps`); Genos-m ← nt CDS (`gtdb_proteins_nt_reps`). **No ORF-calling on our side** — GTDB ships both gene-for-gene (219/219, P1-D9), so we inherit its gene calls; never translate/reverse-translate. Contract for the embed scripts: `--model genos-m` reads `.fna`, never `.faa` (the P1-D12 bug).
- **Models:** ESM-2 `facebook/esm2_t33_650M_UR50D` (1280-dim); Genos-m `BGI-HangzhouAI/Genos-m` (1024-dim). Cutoffs per P1-D7.
- **Layer & pooling:** final hidden layer, mean-pooled over tokens (both backends already do this; matches HiFi-NN's ESM-2 650M usage). Deferred Phase-2 ablation: mid-late layer if separation is weak.
- **Normalisation:** L2 → cosine geometry, before any scoring — scale-invariant, standard for FM embeddings, already the metric the Week-2 separation check used (0.963 vs 0.928), comparable across the 1280/1024 dims; the Phase-2 kNN/EVT scorer inherits it.
- **Length/precision:** fp16; truncate at `max_tokens` (ESM-2 1024 aa / Genos-m 8192 nt) + log the truncated fraction (chunk-and-mean-pool if material). For the *fair* separation comparison, restrict to genes both models see fully (≤ 1024 aa), removing the ESM-2 (1024 aa) vs Genos-m (~2730 aa-equiv) length asymmetry.

### P1-D14 — Second snapshot boundary (shorter, recent): benchmark is robust to boundary choice [Phase 1, Track 1]

## Phase 2 — Calibrated Novelty Scorer (Track 1 design, `docs/Track1_phase2_scorer_design.md`)

### P2-D1 — Scorer family: EVT (GPD) on kNN distance is the calibrated headline; raw kNN distance is the baseline [Phase 2, Track 1]
Resolves the D4 fork deferred from Phase 1. The scorer that the title's "calibrated" commits to is **EVT peaks-over-threshold (Generalized Pareto) fit to the tail of the kNN cosine-distance score**; the **baseline it must beat is the raw kNN distance** — which is exactly the family of method the closest prior art uses (HiFi-NN's hand-set 0.38 cutoff, P1-D11). The contribution is the **calibration layer on identical geometry**, not a new representation: the same distance HiFi-NN thresholds by hand becomes a GPD tail p-value = a calibrated false-flag rate (Pickands–Balkema–de Haan: threshold exceedances converge to a GPD). Score: `d(x)` = mean cosine distance of query `x` to its `k` nearest characterised neighbours; calibrate on the reference's leave-one-out kNN distances, fit GPD above threshold `u`; `p(x) = ζ_u·(1 − G(d(x)−u; ξ, β))` = P(a characterised protein sits this far out) = the checked error rate; novelty `s(x) = 1 − p(x)`. **Rejected as headline: per-class EVM / OpenMax** (a Weibull tail per Pfam family) — the panel has thousands of families, many with a handful of members → thin, unstable per-class tails; and we score distance from *all* known space, not family membership. Kept as a **secondary comparison** only if family counts allow (P2-D5). Alternative also considered and rejected: "spec both EVT variants + density foils, pick empirically" — more implementation load on Track 2 and a less committed headline than the data and the narrative warrant.

### P2-D2 — Reference = characterised-at-T₀; queries = dark-at-T₀; mean-of-k cosine score, leave-one-out calibration [Phase 2, Track 1]
Fixes what "characterised space" is and how a distance becomes the raw score. **Reference** (the known cloud the distance is measured to) = characterised-at-T₀ panel proteins (a Pfam-35 GA hit, P1-D3); **queries** (scored) = dark-at-T₀ panel proteins (no Pfam-35 hit); the **4,138 positives** (P1-D12) are the query subset characterised by T₁. **Geometry = cosine** on L2-normalised Phase-1 embeddings (P1-D13) — no re-embedding, the scorer inherits the vectors; distance `= 1 − cosine`. **Score = mean of the `k` nearest characterised distances** (mean-of-`k`, not distance-to-`k`th — robust to one spuriously close reference hit). **Reference calibration = leave-one-out** (each reference protein's kNN excludes itself, includes same-family neighbours = the natural known-to-known spread the tail model needs). **Leakage (P1-D7): the scorer is identical across both arms; only the embedding changes.** ESM-2 = leakage-clean headline; Genos-m = leakage-controlled (positives restricted post-R220 + full-window), reported separately, never pooled.

### P2-D3 — Evaluation wiring: positives → Precision@K (lift); held-out-family → AUROC + calibration (never the biased positives) [Phase 2, Track 1]
The three frozen metrics (blueprint §7) are each fed by a *specific* ground truth, and the load-bearing choice is that **calibration is certified on the controlled ground truth, never on the selection-biased positives.** (1) **Precision@K (ecological validity)** — rank dark queries by `s(x)`, top-`K` precision = fraction that are positives; report as a curve and as **lift over the scored set's own positive base rate** (positives ÷ dark queries ranked — ≈1.4% at natural dark density, *enriched* in the capped embedded set since P1-D6 caps dark negatives; report the exact set value). Lift, not raw precision, is the signal. **Selection-bias caveat (P1-D3) is stated:** positives skew *moderate*-novelty (near-known genes are characterised first; maximal-novelty genes are too far out to be characterised yet), so Precision@K measures **prioritisation value**, not "novelty = characterisability" — a monotone lift is the claim, a perfect top-`K` is not the target. (2) **AUROC (sensitivity)** — from the held-out-family construction (P2-D4), separating held-out members (novel) from retained knowns (known); controlled, no selection bias; report the distribution over families. (3) **Calibration check (honesty — the headline)** — reliability diagram on the **held-out-family** ground truth (predicted p-value bins vs observed novel-fraction vs diagonal), tests whether the GPD's checked error rate is honest. One line: **held-out-family certifies the score is sensitive and honest; the retrospective positives show it surfaces real, later-confirmed biology.**

### P2-D4 — Held-out-family protocol: withhold → score → aggregate, matched controls, leakage-safe [Phase 2, Track 1]
The controlled novelty ground truth that P2-D3's AUROC + calibration depend on. **Construction:** withhold one Pfam-35 family `F` → remove all `F` members from the reference → `F`'s members become queries labelled **novel** (with `F` gone they should sit far from remaining known space); negatives (label **known**) = a matched sample of characterised proteins whose family is not held out. **Matched controls:** match novel vs known on sequence length, GTDB phylum, and family size, so AUROC reflects novelty detection, not a length/rarity confound. **Leakage-safe by construction:** the embedding may still place `F`'s members near where `F` sat (it saw `F` in pretraining) — that is exactly the stress test (can distance-to-*remaining*-reference flag them anyway?); the test isolates the **scorer's** sensitivity with the embedding fixed, and is not a claim about the embedding's own leakage (P1-D7's job). **Sampling:** all Pfam-35 families with ≥ `m` members; if large, a phylum/size-stratified sample of `N` families (P2-D5), fixed seed → AUROC distribution + pooled calibration curve.

### P2-D5 — Hyperparameters frozen pre-result (anti-fishing) [Phase 2, Track 1]
Declared before any scorer output and not tuned on results — the commitment the metric-freeze already made; change only by a reviewed edit stating a reason (mirrors the `snapshots.yaml` rule). **`k` (kNN)** = headline **5**, sensitivity over `{1,5,10,20}` as an appendix only. **GPD threshold `u`** = the **90th percentile** of reference leave-one-out kNN distances (the *rule* is fixed, not a hand-tuned value), with a mean-residual-life / parameter-stability robustness plot. **GPD fit** = MLE (`scipy.stats.genpareto`), report `ξ`, `β`, and a tail goodness-of-fit (QQ / Anderson–Darling). **Precision@K** `K ∈ {50,100,500,1000}` + full curve; lift = Precision@K ÷ (positives ÷ dark queries ranked). **Held-out families** = all Pfam-35 families with ≥ **`m`=5** members; if > 500, a phylum/size-stratified sample of 500; seed = the Phase-1 panel seed. **Fair ESM-2-vs-Genos-m** = restrict to genes ≤ 1024 aa (P1-D13). All sampling seeded and recorded in `config/scorer.yaml`, committed before the first run.

## Phase 4 — Extension: Layer 4 Multi-Signal Convergence (Track 1 design, `docs/Track1_phase4_extension_design.md`)

### P4-D1 — Phase-4 extension = Layer 4 multi-signal convergence; chosen over Layer 2 (structural fusion) [Phase 4, Track 1]
Fixes the blueprint's Phase-4 extension (§7 "a limited extension from Layer 2 or Layer 4, if time permits") as **Layer 4 — multi-signal convergence** (§6), operationalizing the §4 "independent lines converge" principle: combine independent novelty axes, assign high confidence **only where they agree.** **CHOSEN OVER Layer 2 (structural fusion)** because Layer 2 is the one compute-constrained path in the whole project (full ESMFold is "Limited" on the M1 / needs the ProstT5 substitute, §9), whereas Layer 4 reuses signals already in hand + adds a genuinely **embedding-independent** axis at ~zero cost, and it extends the Layer-3 convergence result (P3-D6) into a full multi-axis version. **Two axes, of DIFFERENT kinds so agreement is real evidence:** (A) **sequence-embedding novelty** = the frozen Layer-1 ESM-2 EVT score per dark query (`esm2_novelty_scores.csv`); (B) **genomic-context novelty** = how dark a gene's genomic neighbourhood is, computed from GTDB gene-order (encoded in the protein ID `<contig>_<ordinal>`): fraction of a gene's ±`window` on-contig neighbours that are dark-at-T₀ — guilt-by-association inverted into a novelty signal, **embedding-free** so it shares no input with axis A. **Layer 3 REJECTED as axis B** (its negative-selection score is also ESM-2-embedding-based, correlated +0.32 with Layer 1 → weak independence). **Genos-m per-query novelty = optional THIRD axis**, needs a cloud re-score (only its held-out-family AUROC exists, P2-D11), foldable later, not required for the claim. **Convergence method:** report axis independence (Spearman + top-K Jaccard) FIRST as the precondition (convergence is only real multi-evidence if the axes are independent), then the high-confidence convergent set = above the per-axis quantile on BOTH axes (agreement, not a weighted sum). **Frozen pre-result (`config/convergence.yaml`, anti-fishing):** window=5, min_neighbors=4, quantile=0.90, top-K∈{50,100,500,1000}, seed=42. **Eval read through the §10/P2-D6 selection-bias lens:** positives are the *near-known* genes, so any good novelty axis is EXPECTED to deplete them → the claim is prioritisation of the unexplored frontier, not a positive-rate lift; underperformance-on-positives is an acceptable, reportable outcome (as in Layer 3). **USER-buildable component** (`darkmatter/convergence/`); the optional Genos-m third axis is a hands-on follow-up.

### P4-D2 — Layer-4 built + first result: the two axes are independent (convergence is real multi-evidence); both novelty axes surface the frontier [Phase 4, Track 1]
Built `src/darkmatter/convergence/multisignal.py` (genomic-context novelty + convergence stats + high-confidence set), driver `scripts/run_convergence.py`, frozen `config/convergence.yaml` — runs on the existing Layer-1 scores + panel labels, **no GPU / no re-embed**. Context novelty defined for 1,263,926 / 1,341,100 panel genes (94%; rest = contig-end/short-contig, correctly omitted not zeroed); **31,712 scored dark queries carry BOTH signals** (3,843 positives; base rate 12.1% — the P2-D3 *enriched* rate in the capped embedded set, not the ~1.4% natural density). **THE KEY RESULT — the axes are independent:** Spearman(EVT, context) = **−0.05** (≈ 0), top-K Jaccard **K50=0.000 / K100=0.000 / K500=0.003 / K1000=0.012** — the top genes by each axis are almost completely disjoint → genomic context carries information the embedding does NOT, so convergence is **genuine multi-evidence**, not one signal restated (the exact failure mode that would have sunk it, cf. why one-class-kNN was rejected for Layer 3 in P3-D1). **What requiring BOTH axes buys (positive-rate vs base 0.121):** EVT-top-10% 0.121 (lift 1.00×), **context-top-10% 0.083 (lift 0.68×)**, **convergent-both (325 genes) 0.108 (lift 0.89×)**. Both novelty axes DEPLETE the near-known positives → **this extends the P2-D6 inversion to a second, independent signal**: novelty — whether by sequence embedding OR genomic neighbourhood — anti-predicts near-term characterisation, so the 325-gene convergent set is the high-confidence **frontier the annotation pipeline leaves behind.** **HONEST FRAMING (matches §10 + Layer-3 stance):** convergence does NOT raise precision-on-positives, and it CANNOT against a near-known label — the contribution is (i) the demonstrated **independence** of a new embedding-free novelty axis and (ii) the **high-confidence convergent set** as a prioritisation output, not a positive-rate lift. Note EVT-top at the 90th-percentile is neutral (1.00×) whereas P2-D6's Precision@K inverted (<1×) — the inversion is concentrated in the extreme top-K, and washes to ~1 over the top 10%; consistent, not contradictory. Artifacts: `data/processed/gtdb_R207/convergence_results.json`. Optional next: Genos-m third axis (cloud re-score) — its independence from ESM-2 (different FM) would make a 3-way convergence even stronger.

### P4-D4 — Third convergence axis = compositional/statistical novelty (local, closes Layer 5 partially); Genos-m axis stays cloud-blocked but wired [Phase 4, Track 1]
The offered "optional enhancement" was a Genos-m **third convergence axis**, but that is **cloud-blocked for the M1** — scoring dark queries with Genos-m needs BOTH the Genos-m reference AND per-query embeddings, which live on AWS and cannot run at scale locally (established P2-D7/P2-D10). So to actually DELIVER a 3-way convergence now, I added a **fully-local, genuinely-independent third axis: compositional/statistical novelty** — the Mahalanobis distance of each dark query's amino-acid composition from the characterised reference's composition distribution (`scripts/compute_composition_novelty.py` → `composition_novelty.csv`; functions `aa_composition` + `mahalanobis_novelty` in `darkmatter/convergence/`). Positive-rate lifts: evt-top 1.00×, context-top 0.68×, **composition-top 0.26×** (compositional outliers deplete positives HARDEST = the deepest dark matter), **3-way convergent (108 genes) 0.53×**. The 108 triple-convergent genes = **3.4× more than the ~32 expected under full axis independence** (0.10³·31,712) → **real convergence beyond chance**, driven by the shared underlying novelty (evt~composition correlation + context orthogonality). **INTERPRETATION (consistent with P2-D6/P4-D2):** every independent novelty axis anti-predicts near-term characterisation, and the effect compounds across axes → the 108-gene triple-convergent set is the highest-confidence frontier the annotation pipeline leaves behind, established by THREE independent lines of evidence (the §4 principle fully realised). **HONEST CAVEATS:** (i) composition novelty (AA-frequency Mahalanobis) is a first-order statistic and may partly track length / short-ORF effects — a fuller Layer 5 (k-mer entropy, positional structure, shuffled/intergenic coding-vs-noise controls) is the natural extension; (ii) evt~composition are moderately correlated (0.26), so those two are not fully independent — but genomic context is independent of both, so the 3-way is not one signal in triplicate; (iii) as in P4-D2, no precision-lift claim against the near-known positive label — the contribution is the independence + the high-confidence convergent set. ### P4-D7 — reembed_eval.py's held-out-family AUROC fixed from O(F*N^2) to O(N^2): unblocks the full 903-family Genos-m eval [Phase 4, Track 2]
P2-D11 flagged the full 903/3,109-family Genos-m run as blocked because `heldout_auroc`'s per-family loop recomputed a full reference-vs-reference kNN from scratch for every held-out family — fine at the 300-family cap, not at 903+. Rewrote it: instead of an O(N^2) reference-vs-reference distance computation *per family*, precompute each reference point's top-`m` nearest neighbours **once** (`_topm_neighbors`, chunked over query rows so peak memory is `chunk x N`, never the full `N x N` matrix — same memory discipline the original per-family `knn()` already used, just paid once instead of `F` times), then for each held-out family filter out any precomputed neighbour that falls inside it and take the top-`K` of what's left (`_knn_dist_excluding`). `top_m=500` comfortably exceeds every family size in this benchmark. Centering now uses the reference's **global** mean instead of a per-fold family-excluded mean — a deliberate approximation, not an oversight: P2-D9 already measured this exact simplification's effect on the real 15,360-point reference at ~0.001–0.003 AUROC, i.e. negligible at this project's actual scale.
**Validated, not just written:** the **raw (uncentered) path reproduces the original per-family implementation bit-for-bit** on multiple synthetic reference sets (exact match to 1e-9, both trivially-separable and heavily-overlapping cluster configurations) — the core algorithmic change is provably lossless. The **centered path's global-mean approximation shows more divergence on these small synthetic tests (up to ~0.09 AUROC)** than P2-D9's real-scale measurement (~0.002) — expected and not a red flag: synthetic tests use tiny N with large family-to-reference fractions (removing one family shifts the mean a lot), while the real benchmark has small families against a >10k-point reference (removing one shifts the mean almost nothing). The approximation's actual error at this project's scale was already measured directly, not estimated from a toy case.
**Could not validate end-to-end against the real 15,360-point ESM-2 reference locally** — the dev machine hit real memory pressure (available RAM fell to ~870MB mid-session, another process's-worth of headroom gone) and even a 56MB numpy allocation failed; deferred to validating on the cloud GPU instance (far more RAM) before spending on the actual Genos-m run. Motivated a second fix en route: the first version of this optimisation materialised the full `N x N` similarity matrix once, which is *faster* but reintroduces exactly the memory blow-up the original code's own docstring said to avoid — reworked to the chunked top-`m` design above before it was ever run for real, so the memory-pressure incident caught a real design flaw, not just bad timing.
